HOLOS A triplestore built from the four things that exist separately and nowhere together.

Worst-case-optimal joins, a durable RDF-1.2-native transactional store, SHACL enforced on the write path, and versioned shape-governed graph partitions with incrementally maintained views. Each one shipped somewhere. Their combination is the thesis.

P0 and the security layer are built. 3,145 of 3,284 W3C tests pass, and every one of the 139 failures is upstream — not one is a HOLOS bug (§15). Everything above L3 is still design. Storage has two backends behind one trait; SHACL_Engine is adapted and fed from the store 3.6× cheaper than parsing, with a native evaluator alongside it for incremental revalidation at 161× a full pass. GeoSPARQL and a SPARQL-over-HTTP server with a YASGUI console are up, and access policy covers both with no extra code. Holons tick: a boundary enforced on the write path, per-triple provenance through RDF 1.2 reifiers, and a validated commit costing 41× less than a full pass. §14 is the security argument, §16 the measurements, and §11 marks where the line falls.

01Verdict

Yes — and the reason it is worth doing is not “a faster triplestore”. There are already fast triplestores. Rebuilding one of those is a losing race.

What does not exist as a single system, as of August 2026, is the combination of four things:

  • 01Worst-case-optimal join execution over a tensor-shaped index that slices on any dimension.from Tentris
  • 02A durable, transactional, RDF-1.2-native store with a conformant SPARQL front end.from Oxigraph & Jena TDB2
  • 03SHACL as a write-path subsystem, not a batch library that reloads the graph.from SHACL_Engine, generalised
  • 04Versioned, shape-governed partitions with incrementally maintained views.from the Holon model

Everything below is subordinate to that. If a design decision does not serve one of the four, take the boring option and reuse someone else’s code.

The honest counter-position — every way this fails — is in §12. The five decisions still genuinely open are in §13.

02What each input actually contributes

Read as a pair of columns: what to take, and what to consciously leave. The second column is the more useful one — every system on this list has a limitation that is an artefact of its own scope rather than a mistake.

Oxigraph
Take

The crate decomposition — oxrdf, oxttl, oxrdfio, oxjsonld, spargebra, sparesults, oxsdatatypes. Conformance-heavy, boring, already correct, MIT/Apache-2.0. The 6 + 3 column-family index layout. Preliminary RDF 1.2 and SPARQL 1.2 support already in tree.

Leave

The evaluator. The project says plainly that SPARQL query evaluation has not been optimised yet: tuple-at-a-time iterators, pairwise index-nested-loop joins, 128-bit StrHash term keys, no cost model.

pwin/SHACL_Engine
Take

Interned terms as integers; three fully sorted flat arrays (SPO/POS/OSP) with binary search instead of hash maps; compile shapes once into flat IR; deterministic, byte-reproducible reports; 418 of 426 W3C conformance tests passing.

Leave

Its structural limits, all artefacts of being a library rather than part of a store: whole graph must be resident; loading dominates runtime (validation is under a quarter of wall clock at 100k instances); named graphs flattened into one; single-pass rules needing --iterate-rules N. A store fixes all four for free.

Apache Jena 5.5
Take

The RDF 1.2 model decisions: StatementTerm as a distinct RDFNode; triple terms permitted in object position only, narrower than the old RDF-star CG; reifiers as ordinary terms. Also the Graph/DatasetGraph/Model layering, ARQ’s extension points, and TDB2’s MVCC — single writer, many readers.

Leave

The JVM, and the object-per-term memory model.

Tentris
Take

RDF as a sparse order-3/4 boolean tensor; the hypertrie, which slices in constant time on any dimension combination and therefore subsumes all six permutation indexes in one structure; BGP → Einstein summation → worst-case-optimal multi-join; hash-consing of identical subtries (2022); incremental insert and delete (ISWC 2025), which removes the historical bulk-load-only objection.

Leave

The research prototype’s scope: SELECT, SELECT DISTINCT and ASK over well-designed BGP + OPTIONAL patterns only. Full SPARQL lives in the commercial fork. The papers are freely implementable; verify the licence of any code you actually adapt.

Holon CG & “What is a Holon”
Take

The four-layer decomposition — Scene (mutable current state), Boundary (SHACL shapes and rules as the legal transitions), Event (append-only provenance and causality), Projection (the externally visible view). And the framing of a graph as a state machine that ticks, where agents read projections and never touch the scene.

Leave

The Game-of-Life metaphor as an implementation guide, and any commitment to a vocabulary that is still a CG draft. Build the mechanism; keep the vocabulary swappable.

RocksDB
Take

The LSM substrate, used fully: column families, prefix bloom filters, SstFileWriter + IngestExternalFile for bulk load, merge operators for counters, checkpoints for cheap consistent snapshots and branches, BlobDB value separation, and user-defined timestamps for MVCC and time travel.

Leave

The assumption that RocksDB should hold the hot join structure. An LSM is excellent as a system of record and poor at the pointer-chasing random access a WCO trie join needs. See §6.2.

03Non-goals

Naming these now is what prevents scope collapse later.

  • Not distributed. Single node, embeddable, with an HTTP server on top. Sharding an RDF graph well is a research programme of its own; the holon partitioning in §9 is the eventual seam if it is ever wanted, but v1 is one node.
  • Not a new data model. Everything, including all holon metadata, is plain RDF 1.2 in system named graphs. The moment holons need a non-RDF representation, the project has failed its own premise.
  • Not OWL-DL reasoning. RDFS and OWL-RL through the rule engine, materialised. No tableau reasoner.
  • Not a property-graph database. RDF 1.2 triple terms give an edge-property model that is good enough; a native LPG view can be a later projection type.

05Term identifiers

This is the first place to deliberately diverge from Oxigraph, and the divergence sets up everything above it. Oxigraph keys quads by a 128-bit StrHash per term, so a quad key runs to about 64 bytes and there is no dense integer space. SHACL_Engine interns to u32 and gets integer comparisons in its inner loops.

A WCO trie index needs the SHACL_Engine property — dense, small, ordered identifiers — because trie fan-out is stored as sorted arrays or roaring bitmaps of child ids, which a 128-bit hash makes impossible.

4-bit tag
60-bit payload — dense id, or the value itself

TermId — 64 bits. Tag decides whether the payload is a dictionary index, an inline value, or a triple-term handle.

TagMeaning
0x0Dictionary-backed IRI — 60-bit dense monotonic id
0x1Dictionary-backed literal
0x2Blank node, graph-scoped
0x3Well-known vocabulary — static compile-time constants for rdf:, rdfs:, owl:, xsd:, sh:, prov:. rdf:type becomes a constant the optimiser can pattern-match on.
0x4Inline xsd:integer — 60-bit, order-preserving two’s-complement bias
0x5Inline xsd:decimal / xsd:double — order-preserving IEEE-754 flip
0x6Inline xsd:date / xsd:dateTime — order-preserving, UTC-normalised
0x7Inline xsd:boolean, and strings of 7 bytes or fewer
0x8Triple term — index into the triple-term side table
0x9–0xFReserved — vector-embedding handles, geometry handles

Two consequences are worth stating outright. Order-preserving encodings turn FILTER(?d > "2020-01-01"^^xsd:date) into an index range scan — the cheapest large win available, and one most stores decline to take. And inline values never enter the dictionary, so a dataset of measurements pays no dictionary cost for its numbers.

Triple terms, and why RDF 1.2 is cheap

A triple term resolves to an (s, p, o) triple of TermIds in a tt column family: deduplicated, recursive. Because RDF 1.2 restricts triple terms to object position — Jena’s StatementTerm enforces exactly this — the index burden is bounded: no permutation index has to handle a triple term in subject position. Reifiers are ordinary IRIs or blank nodes and rdf:reifies is an ordinary predicate, so the Turtle sugar << :s :p :o ~ :r >> decomposes into two entirely conventional triples plus one triple term.

RDF 1.2 costs one term tag and one side table, not a redesign. It is nonetheless the single most important thing to get right early, because retrofitting it later touches every index.

06Storage

6.1  Tier A — RocksDB, used properly

Keep Oxigraph’s layout, which is already the right answer:

spogposgospg gspogposgosp dspodposdosp graphsid2strstr2id ttstats

Six quad orders, three default-graph triple orders that avoid paying for a graph column, and the dictionary, triple-term and statistics families. What changes is how much of RocksDB gets used:

  • Prefix extractor and prefix bloom filter per index family. A ?s :p :o lookup becomes a bloom-filtered prefix seek instead of an iterator walk.
  • SstFileWriter + IngestExternalFile for bulk load. External-merge-sort the encoded quads, write SSTs directly, ingest them. This is the difference between a billion triples in minutes and in hours — and it is the only thing that makes the load-time problem dominating SHACL_Engine’s benchmarks go away.
  • Merge operators for dictionary refcounts and statistics counters, so the write path never does read-modify-write.
  • Checkpoints for consistent backups, and for holon branching — a checkpoint is a cheap hard-linked fork of a dataset.
  • User-defined timestamps for MVCC and time travel. Stated plainly: UDT is still marked experimental upstream. The designed-in fallback is a monotonic version suffix in the key, the TiKV approach, at the cost of writing your own GC.
  • Value separation (BlobDB) for literals above a size threshold.

Delta-encode successive keys within an index family. With dense ids and sorted order this is very effective — which is why dense ids matter for the cold tier too, not only the hot one.

6.2  Tier B — the hypertrie hot tier

The central architectural bet. Worst-case-optimal joins need trie-shaped structures with constant-time slicing on arbitrary dimension subsets and heavy random access. LSM-trees are the wrong shape for that. Rather than compromise, run both.

Tier A is the system of record: durable, transactional, complete. Tier B is a hash-consed hypertrie per hot graph — built lazily the first time a graph is queried, evicted under memory pressure, kept live by the ISWC-2025 incremental insert/delete algorithm, and stamped with the same MVCC version as Tier A.

Tier B is derived state. It is never the authority; it can always be dropped and rebuilt. That property is what makes the correctness argument tractable: the two tiers can be differentially fuzz-tested against each other, and any divergence is a bug in Tier B, never a data-loss event.

Hash-consing — the “Hashing the Hypertrie” result — is not optional here. It is what makes the memory cost of a second full index survivable, because in real RDF the same subtries recur constantly.

Cost, honestly: roughly a doubling of resident memory for hot graphs, plus a second update path. Mitigations are laziness, per-graph granularity, eviction, and disposability. If the memory numbers come in badly at P3, the fallback is to keep the hypertrie only for graphs under a size threshold and serve everything else from Tier A with binary joins — degraded, not broken.

07Query engine

Reuse spargebra for parsing and sparesults for result serialisation. Start with sparopt; replace it once statistics exist.

Statistics

The highest-leverage estimator for RDF is characteristic sets (Neumann & Moerkotte): the distinct predicate-sets occurring on subjects. They give accurate cardinality estimates for star patterns, which is what RDF queries mostly are, and they are what separates engines that plan from engines that guess. Maintain alongside them per-predicate triple counts, distinct-subject and distinct-object counts via HyperLogLog sketches updated through RocksDB merge operators, and per-graph totals.

Built and measured, and the claim above holds by a wider margin than expected: characteristic sets estimate six of seven query shapes exactly, for a mean q-error of 1.1 against the reused optimiser's 2×108. The counts are exact rather than sketched for now — HyperLogLog's couple of percent of error would have muddied the very accuracy measurement it exists to support, and it is a drop-in swap once that question is settled. See §16.

Planning is hybrid, and that is the point

“WCO everywhere” is a trap. WCO joins win on cyclic and join-heavy patterns; binary hash and merge joins win on selective chains and stars. The 2025 SPARQLoscope results are the cautionary evidence — MillenniumDB leans hard on WCO and is not automatically fast, while QLever, with conventional but well-tuned joins, is fastest on basic graph patterns. So: decompose each BGP into connected components, estimate each, and choose per component. The planner must be able to pick either.

Execution

Morsel-driven parallelism over columnar batches of TermIds, Arrow-shaped, rather than tuple-at-a-time iterators. This is the other place Oxigraph’s ceiling is structural rather than incidental. Operators spill to disk for large ORDER BY, GROUP BY and hash builds.

Property paths get dedicated operators — bitmap-visited BFS for * and +, with a transitive-closure cache keyed by predicate, direction and version. Property paths are where most engines fall over on real workloads, and where a new engine can win visibly.

SPARQL 1.2 surface: the VERSION declaration; TRIPLE(), SUBJECT(), PREDICATE(), OBJECT(), isTRIPLE(); @en--ltr base-direction literals; and the tightened OPTIONAL / MINUS / NOT EXISTS semantics. Note the asymmetry in specification maturity: RDF 1.2 Concepts is a Candidate Recommendation (7 April 2026) while SPARQL 1.2 Query is still a Working Draft (20 August 2026). Pin to RDF 1.2 semantics; treat the SPARQL surface as movable until CR.

08SHACL as a subsystem, not a library

Take the SHACL_Engine design wholesale — compile-once flat IR, integer-interned terms, sorted index access, deterministic reports — and change exactly one thing: it reads the store’s own dictionary and indexes instead of loading its own copy.

That single change deletes the dominant cost in its current benchmarks, where loading exceeds validation by roughly threefold at 100k instances. It also fixes the named-graph flattening limitation, because the store already holds per-graph indexes; validation gains an explicit data-graph selector: this named graph, the union, or the whole dataset.

Incremental revalidation

Build a shape → predicate/class dependency index at compile time. On commit, intersect the delta’s predicates with that index to derive the affected focus-node set, and revalidate only those. Without this, SHACL on the write path is unaffordable; with it, cost is roughly proportional to the size of the change. This is the enabling mechanism for the holon Boundary layer.

Rules to fixpoint

Semi-naive evaluation to a genuine fixpoint rather than a single pass with an --iterate-rules N escape hatch, plus DRed-style incremental maintenance on delete. Keep SHACL_Engine’s honesty about the caveats — rules using negation-as-failure are non-monotonic under iteration, and sh:closed interacts badly with inference — but move them earlier: those conditions should be diagnosed by the shape compiler, rejected or warned at compile time, rather than silently producing wrong answers, which is the current failure mode.

09The holon layer

This is the differentiator, and where the modelling ideas stop being conventions and become storage primitives.

Holon layerEngine primitive
SceneA named graph, versioned. The unit of transaction.
BoundaryA compiled shapes graph and rule set bound to that scene, enforced on commit.
EventAppend-only versioned delta log, PROV-O shaped, with RDF 1.2 reifiers annotating individual triples with who, when and why.
ProjectionRegistered SPARQL queries maintained as materialised views.

A commit is a tick

One MVCC transaction, five steps:

  1. Apply the delta to the scene.
  2. Run boundary rules to fixpoint.
  3. Validate against boundary shapes — on violation, abort or admit-and-record, per holon policy.
  4. Append the event, with reifier-annotated provenance.
  5. Incrementally refresh the affected projections.

Projections are incrementally maintained using Z-set and differential-dataflow techniques — the DBSP line of work. This is the piece that makes the holon story a database contribution rather than a naming scheme: agents query projections, projections are cheap because they are maintained by delta rather than recomputed, and the scene is never exposed. The Holon article’s “clean architectural separation between reading state and triggering transitions” is, in database terms, precisely read from an incrementally maintained view, write through a validated transaction.

The honest restriction: general SPARQL is not incrementally maintainable. Restrict registered projections to a maintainable fragment — BGP, filters, projection, distinct, simple aggregation over that. Anything outside the fragment is accepted but recomputed on read, and the registry says which regime a projection is in. Pretending otherwise would be this design’s worst possible lie.

Time travel and branching fall out of the substrate: AT VERSION n and AT TIME t reads use RocksDB user-defined timestamps or version-suffixed keys, and a branch is a checkpoint plus a fresh event-log head. Auditability — which the Holon article flags as an explicit architectural choice — becomes a per-holon retention policy rather than a schema decision.

All holon metadata is itself RDF, in a system graph, queryable with ordinary SPARQL. No new model.

10Interfaces

Embedded Rust API first. Then SPARQL 1.2 Protocol and Graph Store Protocol over HTTP — the Fuseki-equivalent. Then PyO3 and WASM bindings, following the pattern both Oxigraph and SHACL_Engine already use.

One optional module earns its place: text and vector indexes exposed as SPARQL service or property functions, for hybrid retrieval. This is the concrete reason an LLM-agent system would choose this store over an incumbent, and it aligns with the Holon CG’s stated interest in grounding conversational and computational systems.

12Risks, and how each one kills the project

Severity: ■■■ fatal if unmanaged  ·  ■■□ serious  ·  ■□□ manageable

■■■
Two index tiers, two update paths
The most likely source of silent corruption. Mitigation: Tier B is strictly derived and disposable; differential property-based testing against Tier A on every commit in CI; a VERIFY operation that rebuilds and diffs.
■■■
“Why does this exist?”
The strongest risk of all. QLever is faster today; Oxigraph is more mature; RDFox reasons better; Fluree already ships versioning. Mitigation: the answer has to stay the four-way combination in §1, and specifically the holon layer. The moment this becomes “a slightly faster triplestore”, it should stop.
■■□
Hypertrie memory cost
Could make Tier B unusable on real datasets. Mitigation: hash-consing, per-graph laziness, eviction, size-threshold fallback. Measure at P3 before committing further.
■■□
Incremental view maintenance for SPARQL
Only a fragment of the language is maintainable. Mitigation: state the fragment in the API, recompute outside it, never pretend.
■■□
SPARQL conformance long tail
Chronically underestimated by everyone who has tried. Mitigation: P0 exists precisely to absorb it, and reusing spargebra, sparesults and oxrdfio removes most of it outright.
■□□
RocksDB user-defined timestamps are experimental
Time travel and MVCC depend on them. Mitigation: version-suffixed keys as a designed-in fallback, with the abstraction boundary placed so the swap stays local.
■□□
Specifications in motion
SPARQL 1.2 Query is a Working Draft; SHACL 1.2 Core is a Working Draft (3 August 2026); the Holon CG has published no specification yet. Mitigation: pin to RDF 1.2 Concepts (CR, 7 April 2026), keep the SPARQL surface behind a version flag — the VERSION declaration exists for exactly this — and treat holon vocabulary as configuration.
■□□
Licensing
Oxigraph is MIT/Apache-2.0 and the Tentris research repo is Apache-2.0/MIT, so both are reusable; Jena is Apache-2.0, readable as a reference. Mitigation: the hypertrie library’s own licence needs checking separately, and a commercial Tentris exists — implement from the papers rather than copying code into this tree unless the licence is verified.

13Open questions

Five decisions this study does not settle. Each one is a fork, not a detail. One of them — Q2 — has since been narrowed by measurement rather than argument.

  1. Quads or holons as the storage primitive?
    This design keeps quads and layers holons above. The radical alternative makes the holon the primitive and derives the dataset view — buying tighter versioning and cleaner isolation, costing interoperability with every existing RDF tool. The conservative choice is taken here; it should be a conscious decision, not a default.
  2. Is the hypertrie worth it given a good cost-based optimiser? partly answered
    The precondition holds: characteristic sets cut mean q-error from 2×108 to 1.1, and mis-estimation costs a measured 3× on a five-pattern query (§16). So accurate planning is both achievable and worth having. Still open is Q2 proper — whether a well-planned binary join leaves anything for a worst-case-optimal join to win. That needs a planner consuming the statistics, and the reused optimiser offers no injection point, so P3 is now gated on a build decision rather than on enthusiasm.
  3. How do blank nodes scope across holon versions and branches?
    Skolemise on write, or carry graph-scoped labels? Skolemisation is simpler and makes diffs meaningful; it changes what round-trips.
  4. Does the Boundary layer double as the authorization surface?
    If agents only ever read projections, it can. That is an attractive property, and it needs a security review before anything relies on it.
  5. Which benchmark is the target?
    SPARQLoscope is the most comprehensive current option and should be the reported number, with WatDiv and the Wikidata query logs alongside for join-heavy and real-world coverage respectively.

14Security

§13 Q4 asked whether the holon Boundary layer could double as the authorization surface. It can — but only if enforcement sits in one specific place, and only if three other subsystems are given their own rule.

14.1  Enforce at the scan, never in a query rewrite

Every read reaches data through one function — quads_for_pattern, wrapped by the dataset view. Policy is applied there and nowhere else. That yields a property worth stating formally, because it is the entire security argument:

The property

For a principal A under policy P, the answer to any query Q equals the answer to Q evaluated over the sub-dataset that A is permitted to see.

The usual alternative — rewriting the SPARQL algebra to insert authorization filters — is a leak generator. There is always an operator the rewrite forgot: a property path, a MINUS, a NOT EXISTS, a subquery, an aggregate that counts a row it may not display. Filtering at the scan cannot be routed around, because nothing above the scan has another source of quads. The implementation carries a test named for exactly that — policy_survives_every_operator_that_defeats_query_rewriting.

14.2  Granularity

Five levels. The one that matters most is the second: a named graph is already a column in every index key and a first-class filter, so per-graph authorization costs almost nothing — and a named graph is a holon’s scene.

LevelGovernsCost
DatasetWhether this principal may open the store at allfree
Named graphThe holon-shaped unit. Read, write, validate, administer — per graphone integer lookup
PredicateHiding a sensitive column across every graphone integer lookup
Graph × predicateThe exception case: HR may see salaries, but only in the HR graphone integer lookup
LabelA lattice of level + compartments, against the principal’s clearanceone integer lookup

Specificity decides, and at equal specificity deny wins. Exceptions therefore live in the principal match rather than in a competing allow — a Not combinator exists because “deny this to everyone except role R” is the commonest shape a real policy takes, and specificity cannot express it. Clearance is checked before the rules and is not overridable by them: a label says the principal may not know the data exists, and no allow rule elsewhere should be able to undo that.

14.3  Why it is affordable

Evaluating rules per quad would be hopeless. A policy is compiled against a store and a principal into sets of dense TermIds, so a per-quad check is a couple of integer lookups. This is the §5 dense-identifier decision paying off a second time; a 128-bit hashed term key would make these sets far more expensive.

Compilation introduces one hazard, and it fails in the dangerous direction. A rule naming an IRI the dictionary has never seen cannot resolve to an id, so it enforces nothing — and if that IRI later arrives in the data, the compiled policy is less restrictive than the policy it came from. Compiled policies therefore record the dictionary size they were built against and report themselves stale, and a session recompiles rather than trusting a cached decision.

14.5  Enterprise interoperability

HOLOS authenticates nobody. Verification — OIDC/OAuth2 signatures, Kerberos/SPNEGO, mTLS, SAML — belongs at the edge: an HTTP front door, a sidecar, or the embedding application. What crosses the boundary is an already-verified claim set. That keeps cryptography off the query path, and it means HOLOS interoperates with whatever identity system is already deployed rather than competing with it.

The translation is the interesting part: a principal is RDF. Claims become triples in a system graph, so an access rule can be written against a principal using the same vocabulary as everything else. There is no second policy language to learn, or to get wrong.

One escaping detail worth naming: a subject claim is attacker-influenced text, and it is concatenated into a principal IRI. It is percent-escaped, and there is a test that a subject containing IRI syntax cannot forge another principal’s identifier.

14.6  The three places information escapes the scan

§14.1 holds only because every read goes through one door. Three subsystems can carry information around it. None of these is implemented yet — they are constraints on P4 and P5, recorded here so they are not discovered later.

Statistics
Predicate counts, HLL sketches and characteristic sets are computed over the whole store. A global count tells a principal about data they cannot read. Rule: statistics are policy-scoped or operator-only, and never reach a principal-visible EXPLAIN.
constrains P2
Materialised inference
A rule deriving a visible triple from hidden premises leaks the premises. Rule: a derived fact carries the least upper bound of its premises’ labels. A rule engine that ignores this launders restricted data into an unrestricted conclusion.
constrains P4
Projections
A view computed with elevated privilege and read by a low-privilege agent is a declassification. That is a feature — it is how an agent-facing surface is made safe — but it must be explicit: a projection declares its own label and someone with admin authority signs it off.
constrains P5

14.7  Write-side authority

  • Deleting requires read as well as write. Otherwise “did the delete succeed” is an oracle for whether hidden data exists.
  • Administer is a separate mode from write. Authority to change the shapes, rules or policy is not authority to change the data; conflating them turns a data-entry role into a privilege-escalation path.
  • The event log is append-only. No mode grants the right to rewrite history — auditability a sufficiently privileged principal can erase is not auditability.
  • Boundary shapes gate what may be written; policy gates who may write it. Both run inside the same commit.

14.8  What is not claimed

  • No covert-channel resistance. Timing and resource-exhaustion channels are not addressed. A principal who can measure query latency can probably learn something about the volume of data they cannot read.
  • No cell-level redaction. A quad is visible or it is not; there is no “return the row with the object masked”. That is expressible as a projection and belongs there.
  • No formal verification. The §14.1 property is argued from the chokepoint and tested against the operators known to defeat rewriting. It is not proved.
  • No encryption. Deliberately out of scope for this layer — see §14.5.

What is actually under test

spargebra, oxttl and spareval are reused from Oxigraph and already conformance-tested upstream. Running the suites straight would mostly re-measure someone else’s work. What is new is everything between — the term encoding, the nine-order index, the dataset view — so the suites are run in a shape that isolates exactly that.

RDF suites: round-trip
Parse the input, load it into the store, read it back, compare up to blank-node isomorphism. A difference is a HOLOS bug: a literal the inline codec mangled, a triple term the dictionary lost, a quad an index dropped. 2,447 tests round-trip with no change.
tests §5 and §6
SPARQL suites: an oracle
When a query test fails, the same query is re-run through the same evaluator over an oxrdf::Dataset — the reference storage spareval ships with. Agreement means the storage is faithful and the gap is in the evaluator; divergence is a real bug. All 25 SPARQL 1.1 mismatches agree with the reference.
the §12 differential rig, early

Each suite has a checked-in known-failure list. A run fails if a passing test starts failing and if a listed test starts passing — the second direction matters as much, because a stale list is a list nobody trusts.
guards every later phase

SHACL is measured differently, and the failures are ours

The RDF and SPARQL suites test storage under a reused front end, so a failure there is usually upstream. SHACL is not like that: holos-shacl is new code all the way down, so every SHACL failure is a HOLOS failure, and the table says so rather than quietly reusing the “0 own bugs” column above it.

The five remaining SHACL Core failures are one ill-formed-literal edge case, two complex property-path shapes, one numeric comparison and one sh:lessThan. The 44 SHACL 1.2 failures are 1.2 features never implemented — severity and message declared on constraint components rather than shapes, the 1.2 deactivation rules, node expressions.

Getting from 4/97 to 92/97 took three fixes, and two of them were in the harness, not the validator. The expected report was being extracted by following every object from mf:result, which dragged each shape's whole definition — and then each blank-node focus node's data — into the “expected” graph. Only blank nodes reachable through report-structural predicates belong there. Both were found by reading a failing diff rather than reasoning about what was probably wrong. The third was real: "aldi"^^xsd:integer is a well-formed RDF term and not an integer, and SHACL calls that a violation, so comparing datatype IRIs is not enough.

The skips are not a hiding place

101 SPARQL 1.1 tests are skipped, down from 304, and each skip names a roadmap item rather than a mystery: 70 need an entailment regime, which is the reasoner at L4; 25 are upstream evaluator behaviour, confirmed by the oracle differential; 6 are result-format tests the harness does not read. Counting any of those as failures would bury the ones that are actually broken.

The 203 that used to be skipped and now run are SPARQL Update (94), both protocol suites (47), update syntax (55), and the DAWG rs:ResultSet result encoding — which took SPARQL 1.0 from 45% coverage to 93% on its own, and was a harness limitation rather than an engine one all along. The protocol suites run by starting the real server on an ephemeral port and replaying each scripted HTTP conversation against it; both now pass in full, 34/34 and 13/13.

The strongest single result is the one the round-trip gives: the canonicality rule from §5 — inline only when the lexical form is already canonical, so "1"^^xsd:integer and "01"^^xsd:integer stay distinct terms — holds across the whole literal zoo, not just the cases someone thought to write down.

The P1 target was wrong, and here is the evidence

§11 set P1’s exit criterion at 500k triples/s. That number was written before anything had been measured. It is roughly 12× the persistent path’s actual rate, and it is withdrawn rather than left standing as an unearned claim.

Three measurements locate the cost and rule out the obvious explanations:

Not the dictionary
Re-loading the same file into an already-populated store runs at 45k quads/s — only 11% faster than cold, despite allocating no ids and writing no dictionary rows.
warm vs cold
Not an algorithmic defect
100k and 1M load at the same rate. The cost is linear in the data; there is no super-linear behaviour hiding at scale.
100k vs 1M
Partly the log
Buffering writes and skipping the write-ahead log is 2.4× faster (43k vs 18k). Real, and already taken.
bulk vs not

What remains is the per-quad cost of pushing three to six index keys through the memtable — the same whether a key is new or an overwrite. That is precisely the work SstFileWriter ingestion skips, handing sorted SST files to the LSM directly. §6.1 named it; it is not built.

The replacement criterion: P1 exits when SST ingestion lands and the persistent path is measured again, against this 41k/s baseline, on a dataset too large to hold in memory. A target is worth setting once there is a measurement to set it against.

Three tuning attempts did not move the number, recorded so they are not repeated: disabling auto-compaction during the load, enlarging the memtables, and removing the allocations on the term-lookup path. The first two stay in the code because they are correct on their own terms. None of them was the bottleneck.

161×. That is what makes SHACL affordable on the write path, and therefore what lets the holon Boundary gate every commit rather than run as a nightly batch.

Two smaller results are worth keeping. Compiling the shapes costs half a millisecond — the compile-once property doing its job, so holding compiled shapes and validating repeatedly is free. And validation does no loading at all: the 2.2s load is the store's, paid once and shared with the query engine and the policy layer. A validator that is a library pays it again into its own structures, and deleting that is what §8 set out to do.

The honest qualifier: this is not a like-for-like benchmark against SHACL_Engine. It measures the mechanism the design predicted, on a workload chosen to exercise it. A comparison on identical inputs is still owed.

What a holon tick costs

100,000 instances, 300,000 triples in the scene, a four-shape boundary. Validation runs inside every commit.

Why this ratio decides §9

41× cheaper than a full pass. Validation inside every commit is only sane if a commit costs the size of its own change. At full-pass cost a Boundary would be a nightly batch job wearing a transaction's clothes, and the holon model would collapse back into “validate the warehouse overnight and hope”.

A refusal costs slightly more than an acceptance, because it also undoes what it applied. That is the right way round: the system pays for rejecting bad data, not for accepting it.

The honest reading of 165 commits/s: it is not a high-throughput write path and is not meant to be. It is the cost of a fully validated, fully attributed commit against a non-trivial scene — the alternative being 4/s if every commit revalidated everything.

What the planner is flying blind on

§7 claims characteristic sets are what separates engines that plan well from engines that guess, and §13 Q2 makes P3 conditional on that claim. Both were assertions until this.

The reused optimiser reorders joins with an estimator that is a fixed lookup table: ?s <p> ?o is estimated at 1,000,000 rows whether that predicate occurs three times or three million. It has no access to the data at all — which is not a criticism, since an optimiser shipped as a library without a store has nothing to consult. But it is exactly the gap a store-aware estimator fills, so both were run against the same queries and the same ground truth. 20,000 people and 100 organisations; 86,967 triples; three distinct subject shapes.

The row that matters most

A star over two predicates that never occur on the same subject. It has zero answers, and the constant table predicts a billion rows — the single worst thing an estimator can do, because a planner told to expect a billion rows will build for a billion rows. Characteristic sets return 0, because they record which predicates actually co-occur rather than assuming predicates are independent. In real RDF they are strongly correlated: entities of the same kind carry the same properties, which is exactly why the naive product of selectivities goes wrong.

The one case this gets wrong, and why. The four-predicate star scores 2.0 — 10,000 estimated against 20,000 actual. Its rdf:type ex:Person arm has a bound object, and the estimator divides by the number of distinct objects for rdf:type, which is 2, assuming subjects split evenly between them. They do not: 20,000 of 20,100 are people. The standard fix is a most-common-values list per predicate, which every mature optimiser keeps. It is deliberately not implemented, because tuning until the benchmark reads 1.0 would be fitting the estimator to its own test.

Does being wrong cost anything?

A badly calibrated estimator can still rank alternatives correctly, in which case the numbers above are ugly and the plans are fine. So: the same five-pattern query, returning the same single answer, with its most selective pattern written first and then last. One pattern matches exactly 1 triple in 150,021; the others match 50,000 each.

Written orderRowsTime
Most selective pattern first10.0777s
Most selective pattern last10.2352s — 3.0×

Written order survives into the plan. The estimator cannot tell a 1-row pattern from a 50,000-row one, so it cannot fix a bad order, and the query pays 3× for how it happened to be typed. Five patterns is a small query; the penalty grows with the number of orderings available.

What this settles, and what it does not

It settles the precondition for §13 Q2: accurate estimates over RDF are cheap and available, and inaccurate ones cost real time. It does not answer Q2 itself, which asks whether the hypertrie beats a well-planned binary join. That needs a planner consuming these statistics — and there is no injection point, since Optimizer::optimize_graph_pattern is a free function the evaluator calls internally. So P3 is now gated on a build decision, own the planner, rather than on enthusiasm. Deliberately not claimed: this measures estimation quality and one plan-order penalty, not query throughput.

Two other numbers worth keeping

489,479 dictionary terms for a million triples. Every xsd:integer, every xsd:float and every city name of six bytes or fewer inlined into its id and never reached storage — the §5 encoding doing exactly what it was designed to do.

48 MB on disk from a 90 MB source, carrying three index copies of every triple. Dense 64-bit ids plus LZ4 are why; a 128-bit hashed key would roughly double the index.

18The holon skeleton

The point the rest of the project was aimed at. Nothing else in the workspace does this: a named graph whose invariants are enforced on the write path, with per-statement provenance, at a cost proportional to the change.

A commit is a tick

  1. Apply the delta to the scene — a named graph, authorised per quad through the same Session everything else uses.
  2. Run boundary rules to fixpoint. Not built — left visible in the code rather than quietly skipped.
  3. Validate against the boundary, incrementally. This is what §8's revalidation was built for.
  4. Append the event, with reifier-annotated provenance — written whether or not the commit was admitted.
  5. Refresh projections. Recomputed, not maintained.

Where RDF 1.2 stops being a checkbox

Provenance about a statement has always been awkward in RDF: standard reification is four triples with no semantics, and a named graph per statement does not scale. A reifier plus a triple term says it in two triples and says it exactly:

_:changerdf:reifies <<( ex:alice ex:email "new@example.com" )>> ;
holos:inTick _:tick ; holos:operation holos:Added .

The tick node carries who and when once; each change points at it. And because §5 already made a triple term cost one term id, the log is not expensive to keep.

Three refusals worth naming

A tick is not atomic
A refused commit is undone by a compensating write, not a rollback. A crash between applying the delta and writing the event leaves the two disagreeing. This is the honest limit of a skeleton — it shows the shape, it is not yet a thing to put a ledger in.
needs §6.1 MVCC
Rules do not fire
SHACL-AF fixpoint evaluation exists in the adapted engine, but only over a bridged snapshot — so firing rules per tick would mean re-bridging per tick. Exactly the gap the immutable engine graph leaves.
needs a merge-in-place
Maintained projections are refused
Regime::Maintained returns an error rather than silently recomputing. Claiming a guarantee the build does not provide would be worse than declining it, and a caller that asked for incremental maintenance deserves to know it did not get it.
needs Z-set IVM

17Geospatial, and the web layer

Two additions that both turned out to inherit more from the layers below them than they added of their own.

GeoSPARQL

spargeo supplies 43 GeoSPARQL functions — the topological relations of all three families (Simple Features, Egenhofer, RCC8), plus distance, buffer, convex hull, envelope, boundary and the WKT/GeoJSON accessors. Registered on the evaluator, so they compose with the rest of SPARQL and with everything underneath: a WKT literal is a typed literal taking the dictionary path like any other, and access policy applies to geometry — denying geo:asWKT makes a spatial join find nothing, because §14's property gets no geospatial exemption.

What is missing
These are filter functions. geof:sfWithin scans every candidate geometry rather than probing an index. Fine on a small dataset, not on a national gazetteer.
honest limit
Where the index goes
An R-tree over geometry literals. §5 already reserves term tags 0x9–0xF for geometry handles, so a geometry can carry an index handle in its id.
designed, not built
Why it waits
Routing to that index is a cost-based decision, so it needs the optimiser P2 will build. An index nothing knows how to use is not a feature.
gated on P2

The HTTP layer

holos-server serves the SPARQL 1.2 Protocol with a YASGUI console. What is interesting is how little of it is server code.

Access policy came for free. Every request opens a Session, and no path from a request to the data avoids one, so §14's chokepoint covers HTTP without a line of policy code in the server. Start it with --deny-predicate and that predicate vanishes from every query the endpoint answers; a classified graph disappears from SELECT DISTINCT ?g as well as from its own contents.

Identity stays at the edge. The server reads already-verified claims from forwarded headers — and refuses to read them at all unless started with --trust-forwarded-identity. Trusting those headers on an open port would let any client name its own roles, which is the exact inverse of what §14 is for.

Threading forced a change three layers down. Serving reads from many threads needs Storage: Sync, and the RocksDB backend was holding a WriteBatch across calls — a raw pointer inside it made the whole store un-shareable. The buffer now holds owned bytes and builds the batch at flush. A web server is not usually where you discover a storage-layer constraint, but the &self/&mut self split is exactly what made it a compile error rather than a race.

YASGUI itself is loaded from a CDN rather than adapted — a large minified bundle in an RDF engine's tree makes that tree harder to audit. The consequence is stated rather than hidden: the console needs network access, the endpoints do not, and --no-ui removes it entirely.
