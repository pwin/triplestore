01Getting started

Two binaries. holos is the command line; holos-server speaks the SPARQL 1.2 Protocol over HTTP.

build
deploy/setup.sh          # checks prerequisites, builds, runs the tests
# or on Windows
deploy\setup.ps1

You need Rust 1.87+, and clang plus a C++ toolchain because RocksDB compiles C++ and generates its bindings with libclang. That is the most common cause of a failed first build, so setup.sh checks for it before starting rather than letting the failure surface two hundred lines into a compile. Without persistence you need neither: cargo build --release --no-default-features.

first query
holos query --data examples/hr.trig \
  --query 'SELECT ?name WHERE { GRAPH ?g { ?s <http://example.com/name> ?name } }'

Everything reaches data through one place. There is no path from a query, a dump, a SHACL run or a holon tick to the indexes that bypasses DatasetView. That is what makes the policy guarantee in §4 a property of the system rather than a convention people have to remember.

02Loading data

Seven input serialisations, chosen by file extension — each also gzipped. Six on output.

FormatExtensionReadWriteMedia type
Turtle.ttlyesyestext/turtle

TriG.trigyesyesapplication/trig
N-Quads.nqyesyesapplication/n-quads
RDF/XML.rdf .owlyesyesapplication/rdf+xml
JSON-LD.jsonldyesyesapplication/ld+json
N3.n3yesnotext/n3

TriG and N-Quads carry graph names; the others do not. That makes the choice a correctness question rather than a preference — dumping a quad store as N-Triples silently flattens every named graph into one. holos dump therefore defaults to N-Quads.

Gzipped input, streamed

Every format above also reads with a .gz suffix — data.nt.gz, dump.nq.gz — which is how large RDF is actually distributed, and which compresses about tenfold. Decompression is streamed, so a 60 GB dump costs no more memory than a small one.

Multi-member archives are read in full. Large dumps are often produced by concatenating compressed chunks; that is valid gzip, and a single-member decoder stops at the end of the first chunk while reporting success — losing most of the file without an error. There is a test for exactly that.

loading, and dumping back out
holos stats --data data/*.ttl --store ./var/store --bulk

holos dump --store ./var/store                  # N-Quads
holos dump --store ./var/store --format trig    # nq, nt, trig, ttl, rdf, jsonld
--bulk is 3.3–3.6× faster, and the catch is worth knowing

It buffers writes and skips the write-ahead log: 36k quads/s against 10k on 7.5 million quads, and the advantage grows with the dataset, because the log it skips grows too. The cost is that a load interrupted part-way has to be discarded rather than resumed — the right trade for a load you can simply re-run.

One process per store directory

RocksDB takes an exclusive lock. A second process gets Failed to create lock file: .../LOCK. Stop the server before loading — this is expected, not a fault.

RDF 1.2 triple terms

Triple terms are supported in object position, which is where RDF 1.2 puts them, and rdf:reifies is the way to attach statements about them:

ex:claim1 rdf:reifies <<( ex:carol ex:salary 102000 )>> ;
          ex:statedBy ex:payroll ;
          ex:statedOn "2026-08-01T09:00:00Z"^^xsd:dateTime .

03Querying

SPARQL 1.2 evaluates end to end. Here is exactly how complete that is — both numbers, because one of them alone is misleading.

SuiteCorrectnessCoverageWhat is not run
SPARQL 1.1321/321 · 100%321/625 · 51%Update (149), protocol (47), entailment (70), federation (7)
SPARQL 1.2242/246 · 98.4%246/269 · 91%Update syntax (23)

Read both columns

Correctness is how much of what runs passes. Coverage is how much of the suite runs at all. Quoting only the first would let a store report 100% while skipping half the tests, so both are printed by cargo run -p holos-conformance --example coverage.

The gaps are honest ones and each has a cause: SPARQL Update is not implemented (that is 149 of SPARQL 1.1's skips and all of 1.2's), the protocol suites need endpoints that do not exist yet, and entailment needs a reasoner. SPARQL 1.0's 152 are a harness limitation, not an engine one — those tests encode expected results as RDF, which the harness does not parse.

All four SPARQL 1.2 failures are in the reused parser rather than anything below it, which the oracle differential establishes by re-running each failure through the same evaluator over a plain in-memory dataset.

Result formats

Four, by Accept header over HTTP or --results on the command line: application/sparql-results+json (default), application/sparql-results+xml, text/csv, text/tab-separated-values. CONSTRUCT and DESCRIBE negotiate the RDF formats in §2 instead.

Query planning, and why pattern order matters right now

Write your most selective pattern first

The reused optimiser estimates cardinality from a fixed lookup table — a pattern is guessed at 1,000,000 rows whether its predicate occurs three times or three million. It cannot tell a 1-row pattern from a 50,000-row one, so it cannot fix a bad join order.

Measured cost of that: 13× at 7.5 million quads — and the penalty grows with the data, from 8× at 750k. A well-written query stays linear; a badly written one degrades faster than the dataset does. Characteristic-set statistics that estimate six of seven query shapes exactly are built and measured, but there is no injection point in the reused planner to feed them to, so the fix is to own the planner.

And anchor your closures

A property path costs almost nothing when its left side is a constant: <unit340> ex:partOf* ?a returns 5 rows in 0.22 ms, and even an inverse closure over the whole tree returns 340 rows in 0.70 ms. But the same partOf* with a variable on its left — reached through a join — takes 25 seconds to return 5 rows, because a zero-length path makes every term in the dataset a candidate.

Prefer + to * where you can, and add the zero-length case as a UNION branch that repeats the anchor:

# 1.7x faster, same answers
{ <:p1000> ex:memberOf ?leaf . ?leaf ex:partOf+ ?u }
UNION
{ <:p1000> ex:memberOf ?u }

Repeating the anchor is the part that matters. Writing the second branch as { BIND(?leaf AS ?u) } looks equivalent and is not: a UNION branch does not see ?leaf from outside the group, so the BIND produces nothing and the row for the leaf itself is silently lost. That form returned 4 rows where the path returns 5.

04Access policy

The unusual part of this store, and the reason to read one section carefully rather than skim it.

Policy is enforced at the index scan — not by rewriting queries, and not by filtering results afterwards. The formal property that buys you:

The guarantee

The answer to query Q equals the answer Q would have over the sub-dataset the principal is allowed to see.

That is stronger than it sounds, because it holds for every query shape without anyone having to enumerate them. A COUNT cannot leak the existence of hidden rows; a FILTER NOT EXISTS cannot probe for them; a spatial join gets no geospatial exemption.

  V -.->|"reads"| P["Compiled policy

  Y --> R["Results"]

  N -.->|"fail-closed mode"| X["Error"]

  style N stroke-dasharray: 4 3

Every quad is decided individually, on the way out of the index. Because the decision happens below the evaluator, the evaluator cannot be tricked into revealing what it never received.

Rules

A rule grants or refuses a mode (read, write, validate, admin) over a scope (everything, a graph, a predicate, or a graph-and-predicate pair) to a principal match. More specific scopes win; at equal specificity, deny beats allow.

holos query --data hr.trig --deny-all \
  --allow-graph http://example.com/public \
  --deny-predicate http://example.com/salary \
  --except-role hr \
  --role hr \
  --query 'SELECT * WHERE { GRAPH ?g { ?s ?p ?o } }'

--except-role exists because "deny salary to everyone except HR" is otherwise inexpressible: deny beats allow at equal specificity, so an allow rule for HR would never win. Negation in the principal match is what makes the common enterprise rule writable at all.

Classification labels

Beyond rules, graphs can carry a lattice label — a level plus compartments. A principal reads a labelled graph only if its clearance dominates the label, which is the standard Bell–LaPadula reading.

holos query --data hr.trig \
  --label-graph http://example.com/reviews=3 \
  --clearance 3 \
  --query 'SELECT ?note WHERE { GRAPH ?g { ?s ex:reviewNote ?note } }'

Filter, or fail?

Filter — the default
The query runs and returns what the principal is entitled to. Nothing reveals that anything was withheld. Right when a partial answer is a correct answer for that principal.
Fail closed
--fail-closed turns a refusal into an error. Right when a partial answer would be misread as a complete one — a compliance report, a reconciliation total, anywhere silently missing rows are worse than no answer.

Add --audit to see what policy actually did to a query.

Two of these are ours

43 come from spargeo. geof:buffer and geof:boundary are implemented in HOLOS, because the design document had claimed them before anything checked — a function probe against a live endpoint returned "unknown function" for both. They exist now; the claim was false when it was written.

PREFIX geof: <http://www.opengis.net/def/function/geosparql/>
PREFIX geo:  <http://www.opengis.net/ont/geosparql#>
PREFIX uom:  <http://www.opengis.net/def/uom/OGC/1.0/>

SELECT ?site WHERE {
  ?site geo:asWKT ?g .
  FILTER(geof:sfWithin(?g, geof:buffer(?depot, 5, uom:kilometre)))
}

What geof:buffer actually computes

CRS84 coordinates are degrees, and a metre is not a fixed number of them: about 1/111320 of a degree of latitude everywhere, but of longitude only at the equator, shrinking by cos(latitude) toward the poles. So a metric buffer is computed in a local equirectangular projection centred on the geometry, then converted back.

Accurate
A 1 km buffer measures 3,147,193 m² against an ideal π×10⁶ = 3,141,593 — 0.18% out, which is the polygon approximating a circle.
Latitude-aware
The same 100 km buffer spans twice as many degrees of longitude at 60°N as at the equator. That is correct, and it is what a scalar degree buffer gets wrong.
Not geodesic
Over continental distances, or across a pole, the projection's own distortion dominates. Do not trust it there. A radius in degrees skips the projection and is exact in coordinate space.
These are filter functions, not an index

geof:sfWithin(?point, ?region) evaluates over whatever bindings reach it, so it scans every candidate geometry rather than probing an index. Fine on a small dataset; not fine on a national gazetteer. An R-tree is designed for but not built, and it needs a planner that can route to it — the same planner §3 is waiting on.

06SHACL validation core built

Two validators behind one trait, because they are good at different things and neither dominates.

vendored — coverage
An adaptation of SHACL_Engine, bridged onto the store's own dictionary so it never parses a file. 127/138 on SHACL 1.2 Core against the native evaluator's 94. Use it for a full validation.
native — incremental
Reads the live store directly. Lower coverage (92/97 SHACL Core), but it is the only one that can revalidate a delta — the engine's graph is immutable, so it cannot. That capability is what the holon layer needs.
holos validate --data data.nt --shapes shapes.ttl              # native
holos validate --data data.nt --shapes shapes.ttl --engine vendored
holos validate --data data.nt --shapes shapes.ttl --report     # N-Triples report

Incremental revalidation

This is the mechanism the whole design rests on. At compile time, a predicate → shape dependency index is built. On commit, the delta's predicates are intersected with that index to derive which focus nodes could possibly be affected — and only those are revalidated.

The ancestor walk is not an optimisation — it is a correctness fix. A violating predicate usually belongs to an anonymous property shape that has no targets at all. Restricting to shapes with targets drops it, and five safety tests failed exactly that way before the upward closure was added.

Not yet built: SPARQL-based constraints, SHACL-AF rules, and most of the SHACL 1.2 additions on the native side.

07Holons walking skeleton

A named graph that enforces its own invariants on the write path, and records who changed what.

A holon is a whole that is also a part. Here that means three things travelling together:

Scene
The graph the holon is responsible for — its own state.
Boundary
SHACL shapes that must hold after every commit. Not a nightly report: a precondition for the write landing at all.
Event log
Per-statement provenance in RDF 1.2, so what changed and in which tick is queryable like anything else.

A tick

sequenceDiagram
  participant C as Caller
  participant H as Holon
  participant B as Boundary (SHACL)
  participant S as Scene
  participant L as Event log

  C->>H: tick(delta)
  H->>S: apply delta
  H->>B: revalidate affected focus nodes only
  alt conforms
    B-->>H: ok
    H->>L: record additions & removals
    H-->>C: committed
  else violates
    B-->>H: violations
    H->>S: undo the delta
    H-->>C: rejected + report
  end

A rejected tick costs slightly more than an accepted one (0.0101s against 0.0076s), because it also undoes what it applied. That is the right way round: the system pays for refusing bad data, not for accepting it.

the shape of the event log
_:change rdf:reifies <<( ex:alice ex:email "new@example.com" )>> ;
         holos:inTick _:tick ;
         holos:operation holos:Added .
100k instances, 300k triples, four shapesTime
Full validation of the scene0.250s
Per commit, over 200 ticks0.0061s — 165 commits/s, 41× cheaper
A rejected tick0.0101s
Why that ratio decides whether any of this works

Validation inside every commit is only sane if a commit costs the size of its own change. At full-pass cost, a boundary would be a nightly batch job wearing a transaction's clothes, and the model collapses back into "validate the warehouse overnight and hope". 165 commits/s is not a high-throughput write path and is not meant to be — it is the price of a fully validated, fully attributed commit, against 4/s if each one revalidated everything.

What the skeleton does not have yet

Atomicity — a tick applies and undoes, but that undo is not a transaction; it needs MVCC underneath. Also missing: boundary rules run to a fixpoint, incrementally maintained projections, and time travel.

08Serving it

Full deployment detail is in OPERATIONS.md and deploy/. The two things worth knowing here:

It authenticates nobody, deliberately

Token verification, Kerberos, mTLS and SAML belong at the edge. The server sits behind that edge and reads already-verified claims from X-Holos-Principal, X-Holos-Roles and X-Holos-Clearance — and refuses to read them at all unless started with --trust-forwarded-identity.

The front door contract

Your proxy must strip whatever the client sent under those names before setting its own. Otherwise any caller can add X-Holos-Roles: admin to a curl command and be believed. deploy/Caddyfile and deploy/nginx.conf both do this, and the nginx one is the trap: nginx passes unknown client headers straight through, so all three must be set explicitly.

endpoints
GET  /                   YASGUI console
GET  /query?query=...    SPARQL 1.2 Protocol
POST /query              form-encoded or application/sparql-query
POST /update             501 — no update evaluator yet
GET  /stats              {"quads":…,"dictionaryTerms":…,"namedGraphs":…}
GET  /health             liveness

Writes are the gap

There is no SPARQL Update and no Graph Store Protocol. Writes go through the holos command line against a stopped store, or through the holon API. That is the single largest hole in the HTTP surface and it is stated in the 501 rather than faked.
